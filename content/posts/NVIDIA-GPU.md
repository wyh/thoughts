之前都是调用线上的一些模型用于对话和分析，也不是不可以，费用略高，延迟略大； 和 AI 商量着部署自己的模型，用于一些简单的任务，避免频繁调用线上 API, 不用太顾及 Tokens 消耗。

于是开始了攒机之路

## 正文开始

### 显卡做什么

目前我们用到的主要是 OpenAI 的基础模型 4o 和 4o-mini 以及 Deepseek 和豆包 （主要用于翻译）。 因为翻译是我们的基础核心任务，调用非常频繁，之前想着要不换到线下免费模型，但和 AI 讨论了之后，线下想做到线上的速度，基本不可能，所以就放弃了。

所以线下能做的后来就转化为基础的 Embedding 以及 Rerank. 这两个的好处是模型足够小，显卡带的动，并且速度都是毫秒级别的，这样相比调用远程 API 就很有优势了，毕竟除了电费就没有其他额外的成本（最初的想象，实际上不是的）

因为做 embedding 和 Rerank 其实不需要很复杂的显卡，所以我的显卡算力（两块 3080 20G） 实际上是浪费的，所以和 AI 讨论了之后，我可以部署一项 OCR 业务。 OCR 提取 Markdown 是一项我一直想做的业务，想必能够在多方面提升精确性，但苦于没有算力，以及线上成本很高，等了很久一直没做。

结论就是，显卡目前做三件事情：

1. Embedding
2. Rerank
3. OCR

### 怎么开始

- Rerank 先行 \*
  从这三个业务来说，最容易接入的是 rerank. 为啥？ 因为 rerank 是一块额外的业务，直接从我的现有业务里接入进去，立马就可以启动。 所以我开发上先接入了 rerank, 只花了一上午业务就接好了。 实地测试了一下，速度很可以，大概 100ms 的延迟，能过滤掉很多垃圾的文本，并且不会降低整体的质量。 这样导致我发给 AI 的 Context 有大规模下降。

- 测试 OCR \*

接下来，理论上我应该计入 Emebedding. Embedding 的接入也不算复杂，虽然需要替换模型，原来的方案就不能直接使用（存储的 Embedding 会全部作废）。但是 Embedding 提升质量涉及到对算法的优化，比如切片的优化，以及最重要的， Embedding 文本的优化。所以我打算最后来做这一块。

于是我接下来的任务就切换到 OCR 文本上了。

目前我正在测试 OCR 的效果。

我已经接入了 OCR 模型，这个模型光镜像有 22G, 另外模型有 26G. 我以前没有处理过类似大镜像的东西，操作起来很烦，这些镜像大部分都是从国外下载的。 虽然我知道可以更换镜像源，但我还是坚持从国外下载，不想到处配置这些东西感觉超级超级繁琐。

### 遇到的问题

1. 模型运行的速度不快

我最开始是希望和 Rerank 一样，提供一个 Flash API 来提供服务。 我在本地跑起来后，就后悔了。因为本地跑一次需要若干分钟。显然无法提供类似的 HTTP 服务。所以我又将这个转化为 Celery 任务来跑。

转成 Celery 任务后，还需要设置 solo 模式，避免每次都重启 worker 加载模型，会变得巨慢。

2. GPU VS CPU

我本地是没有 GPU 的，只有 CPU. 所以我先本地跑起来，上生产服务器测试。 因为考虑到 GPU 的存在，所以我根据有 GPU 的方案来实现，但上了服务器就发现根本不是那么回事，好多代码都跑不起来。

最开始的时候，我企图通过 vLLM 来跑， 但我对 vLLM 也缺乏理解，因为和 Pipiline 是类似的模式，但其实不是。 vLLM 就是纯图片，官网推荐使用这种，但这个模式就是纯纯的图片模式，所有的 PDF 都要转换成图片，我猜会很慢。和 AI 确认了之后，也肯定必须先转图片，理论上肯定是更慢的。

于是一番折腾，又不用 vLLM 模式，但在跑的过程中，发现 celery 每跑一个 PDF 都要加载模型，需要 11 秒以上，又是一番折腾，改成 Python 直接加载完模型之后，常驻内存直接跑。

3. 镜像和模型太大了

在中国特定的条件下，下载镜像和模型实在是太慢了。 镜像有 22G, 模型 26G. 下载起来太慢了。
而更要命的是，下载了好几次， 分别是因为：

1. 有一次我删除一个模型的时候不小心删错了， 把整个 pvc 都删掉了，然后重建 PVC，非常惨痛的教育。 还好，不是 AI 干的，我自己干的。
2. 一次是本地的镜像空间(docker image )不够，增大 Docker Volume 的时候，把所有镜像都干没了。 连我原来本地测试的 mysql 都没有了，更惨。
3. 还有一次是网络很慢，中途把电脑带回家，好了，又重来。
4. 还是本地缓存没有了（可能也是空间不够），反复从远端拉镜像，慢的头大。
5. 模型下载的时候，没有去掉老的模型，把所有版本一起下载下来了。
6. modelscope 和 huggingface 的模型缓存是不一样的。 先用 modelscope 下载了，缓存的是 huggingface.

总之，差不多花费了两条的时间折腾了模型和镜像下载，还好买的梯子够用。

4. 噪音问题

噪音是我这个项目最麻烦的问题。 我一共有两台机器，我在搞第二台机器的时候，我就感觉噪音特别大。 我和 AI 一起商量了很多对策， 这包括：

1. 调整 GPU 的风扇曲线
2. 使用静音机箱
3. 购买静音机柜
4. 制造一个静音机柜 (DIY)
5. 找个机房

实际上，首先应该尝试的是第一个 调整 GPU 的风扇曲线。 但我看到这个方法是需要限制 GPU 的功率，并且调整风扇，我觉得这个做法太简单粗暴。 我的直觉认为就应该充分使用 GPU 的效率，并且让风扇尽可能让 GPU 吹起来。 所以我其实是最后才尝试这个方案， 导致走了很多复杂的路。

我在购买静音机柜和机箱之间，当然会想着先购买一个机箱。 但机箱买回来之后，在 Gemini 的指导下，我成功费力把机器装好，尽管很有成就感，但开机的一瞬间我就懵了，因为很吵，一点都不安静。 吵的原因也很简单，因为显卡风扇噪音太大了。 这个时候我应该想到方案 1. 但我还没有，于是我开始思考后面的几个方案。

我尝试比较了各种静音机柜，了解它的构造和原理，最后还是放弃了。主要是这个方案实在太重了，万一买回来不可以用，要花一大笔钱，还很麻烦。 实际上我觉得现在应该来说是够用的。

然后我继续尝试了方案 5， 在和 AI 交流方案 4 的时候。 方案 5 我找了 4 个朋友，有两个人答应可以， 有两个人因为各种原因拒绝了我。 我还搬到我的朋友机房里去了，费了一下午部署好之后发现 Ping 会有 3% - 6% 的丢包，这样就会很慢，并且从我的 Tailscale 网络里断开。 本来来说这个方案是比较靠谱的，也比较省事，不用考虑噪音的问题，但网络却丢包，导致这个方案完全不能用。 尽管路程不是很远，但是搬机器/显示器和键盘非常折腾。 后来朋友告诉我，他们那里还可能会停网（忘记续费）我想幸亏没有搬过去。

最后我来说说方案 4. 方案 4 是我很想折腾，但幸亏没有去做！ 我想这个投入可能超过 1 万（主要是时间成本）。
方案 4 是在办公室里打一个柜子，用静音棉贴满四周。 底部做成镂空，铺上滤网； 顶上开一个空接入一个新风系统。 电脑放在这个柜子里来静音，通过新风系统将热量抽到室外。 这个方案是不是看起来特别有意思，特别的 Geek. AI 甚至给我设计了藤蔓来遮蔽新风系统丑陋的管子，并且把这个角落加一个 ivySCI 的 logo 来点缀，称之为 ivySCI Corner.

但这个方案需要一些工程，比如打一个柜子，贴静音面以及过滤网，以及要打孔安新风。 这算是要投入一笔小的装修费用吧。 不是说不可以做，但我感觉需要投入的时间有点多，我没啥精力应付这个事情，影响我的项目推进。 但这个方案是我最想做的。

最终是写了个程序来监听温度，为不同的温度设置不同的风扇速度来实现噪音控制的。 整体来说，控制在 30% 的风扇转速是完全可以接受的，吹出来的风依然是低于室温的。

目前我还没有完全部署好，整个项目还没有完全跑通，但我预计下周就可以全面上线跑起来了。 期待期待。

### 一点感想

在解决噪音问题上来说，我觉得心理上感觉非常多的压力。有一种挫败的感觉，我分析主要是下面的两个原因：

1. 我感觉为了省钱捣鼓出来的这个方案可能是一个短视的不成熟的方案。浪费太多的时间，没省到钱却浪费了很多钱。比如整个项目中，只有 OCR 是的确省了一点钱， PDF 转 markdown 调用远程 API 1000 页大概 1 美元的成本外，其他的 Embedding 和 Rerank 其实能节省的费用很少。但我却绕了地球一圈，费了很大的力气；
2. 我感觉开办公司如此之久，还需要到处求人，让我感觉很无奈。 按理来说，应该有足够的经费直接购买线上的服务来解决问题，而不是自己捣鼓，浪费时间，效率很低。

这种负面的感觉在我用软件解决了噪音之后，我觉得是可以让我接受的。 现实就是这样，经费很缺，并不能说无节制地调用线上 API 用于日常运营。 比如每天如果需要 100 美金这个开销可能就让这个业务无法继续， 而 100 美金可能也就 3000 - 5000 个 PDF. 经过一番折腾之后，提升了我对 AI 项目的理解，特别是显卡资源稀缺的理解。 这对我当前的投资方向更加坚定，以小观大，大公司也面临很多算力问题。
